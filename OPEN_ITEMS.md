| **OPEN-18** | Web Build Failure: `@prisma/client` Resolution Is Structurally Incompatible Between Root Scripts and `apps/web`'s `prisma generate` | CI/CD | **Open — needs a repo-layout decision, not a dependency fix** | `Web Build (apps/web)`'s "Live DB Concurrency Verification" step runs `scripts/test-db-concurrency.mjs` (repo-root-relative) from the repo root under a `--workspace apps/web`-scoped `npm ci`. That script imports `@prisma/client`, `pg`, and `@prisma/adapter-pg` directly. **Investigated and empirically confirmed both directions of a hard constraint — not fixable via lockfile/package.json edits:** (1) When `apps/web` keeps its own nested `apps/web/node_modules/@prisma/client` (today's `main` state), `apps/web`'s own `npx prisma generate --schema prisma/schema.prisma` succeeds — Prisma's CLI resolves the client relative to the workspace that owns the schema and does not walk up to a monorepo root. But the root-level script then fails (`Cannot find package '@prisma/client'` or, if a stale root copy exists, `SyntaxError: Named export 'PrismaClient' not found` against a non-generated base package). (2) When root and `apps/web` are made to resolve to the exact same `@prisma/client` version (tried: declaring it as an explicit root dependency, pinned exact to match `apps/web`'s `7.8.0`), npm's hoisting dedupes to a single shared root copy — the root script's plain `require`/`import` now finds it, but `prisma generate` then fails with `Could not resolve @prisma/client. Please try to install it with npm i @prisma/client...`, from *both* `apps/web` and repo-root working directories. Tried a `--legacy-peer-deps` full lockfile regeneration under both configurations; the outcome was consistent across clean reinstalls, so this isn't a flake. **Candidate fixes (none applied — this is a decision, not a bug fix):** (a) drop the "Live DB Concurrency Verification" step from the `--workspace apps/web`-scoped job and run it in a job that does a full unscoped install instead; (b) move `scripts/test-db-concurrency.mjs` and its siblings (`test-tenant-isolation.mjs`, `db-seed.ts`, `verify-schema.mjs`, `create-test-user.ts`, ...) into `apps/web/scripts/` so they resolve `@prisma/client` the same way `apps/web`'s own code does; (c) have the CI step copy/symlink `apps/web`'s already-generated client into root `node_modules` immediately before running the script. (b) looks the most durable but is a repo-layout change, so it's left for a human call rather than made unilaterally. The `find-my-way` CVE fix and lockfile-sync fix originally bundled with this investigation have been split out — see OPEN-13/14 and PR #141, which no longer touches `@prisma/client` at all. |
